Why 3-across, not 6-across

Six cells across a 390pt phone gives each cell ~55pt of width — a 10-digit phone number cannot be legible there at any size a 50-year-old owner can read. So the paper logbook's two rows become two labelled blocks (A on top, B below), each block wrapping to 2 rows of 3 in the exact paper order (A-12 → A-7, B-1 → B-6). Cell width becomes 114pt: phone at 14pt mono, amount at 13pt, both readable at arm's length. The whole 12-room board still fits one screen with no scrolling.

Cell anatomy

Every cell is the same 3-line skeleton, so the eye learns one shape: room label top-left · state glyph top-right (bar = booked, ring = locked, nothing = free) · two data lines bottom-left. Booked = phone then amount. Free = "FREE" then "Tap to book". Locked = "LOCKED" then who holds it and the countdown. Nothing is hidden behind a detail view.

Name field & history (M3 / M4)

The sheet is now three fields — name, phone, amount — name first because that's how staff greet the guest. Amount pre-fills from the room's default rate (set in W3), so the common case stays one tap on a chip. The cell then shows a short name above the phone number; the full name lives in History.

History opens from the pill in the app bar — one tap from the board. Grouped by day, newest first, each day showing its own total; search matches name or phone as you type. Cancelled bookings stay in the list struck through, so the owner can see what was released and by whom. Admins see all staff bookings; nothing is per-user hidden.

Multi-night stays · full-day rule

Rooms are sold by the whole day only: check-in 2:00 PM, check-out 11:00 AM, so a stay is always a whole number of nights and one room can never be held by two guests on the same date. Confirming a 3-night booking writes the same guest to all three dates in one action — the sheet shows the check-in → check-out dates and the running total (rate × nights) before the button, so there is nothing to calculate by hand.

Two money figures, each labelled so they never get confused: the board and dashboard show TONIGHT — the sum of per-night rates for rooms occupied on the selected date (15,000 across 5 rooms) — while History shows COLLECTED per day, the stay totals of bookings taken that day. Average rate follows the tonight figure.

On the board a multi-night cell reads N2/3 under the amount — night 2 of 3 — so the owner can see at a glance which guests are mid-stay and which check out tomorrow. Amounts on cells are always per night; History and the dashboard log show nights and the stay total. Shortening a stay releases only the freed dates.

Real-time locking

Tapping a green cell claims a 60-second lock server-side. Every other device turns that cell orange instantly with the holder's name and a live countdown — no dialog, no error message, nothing to dismiss. Lock expires or Confirm lands, and the cell resolves to green or red for everyone. A locked cell is not tappable; the orange fill plus ring reads as "someone's hand is on it".

Every room is sold as a full day — check-in 2:00 PM, check-out 11:00 AM — so a stay is counted in whole nights and no room is ever split across two guests in one day. The board renders whatever this list says — add a room and every phone shows it on next sync. "Out of service" greys the cell and blocks tapping; it never deletes past bookings.
Web ≠ more features

The dashboard is the same board with the space to show more per cell: the staff member who took each booking, and locks attributed by name. Nothing the owner needs on mobile is web-only, and nothing web-only leaks into mobile.

Grid spec (web)

Sidebar 240px fixed · content max 1200px, 36px gutters · 6 equal columns, 12px gap, 118px cell height. Row 1 = A-12 → A-7, row 2 = B-1 → B-6, matching the paper book left-to-right. Below 1100px the grid falls back to the mobile 3-across blocks.

Build notes

One socket channel per date; the client subscribes on date change and unsubscribes on leave. Cell state is a single enum (free | locked | booked) plus optional {phone, amount, byUser, lockExpiresAt} — the same payload drives both platforms, so one component contract covers React Native and Next.js.
